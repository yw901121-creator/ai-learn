# 第 8 章｜Context Engineering：上下文怎麼建、怎麼壓、為什麼會忘

## 一句話重點

**Context Window 再大，也不等於 AI「什麼都記得、什麼都重視」。**  
好的系統會主動建構、排序、壓縮上下文——這叫 **Context Engineering**。

---

## 1. 先澄清：AI 不是有「記憶」，是有「這一輪看得見的字」

每次呼叫模型，本質是把一包文字（tokens）塞進去：

```
[System 規則]
[Skills / 工具說明]
[長期記憶摘要]
[RAG 檢索到的教材]
[最近 N 輪對話]
[當前用戶問題]
        ↓
      模型生成
```

模型**不會**自動知道「哪一段最重要」。  
它只是對整包 tokens 做注意力運算；中間段落還特別容易被忽略（見第 4 節）。

---

## 2. 上下文構建（Context Construction）

### 核心問題
> 給 AI 20 輪對話後，它怎麼知道什麼最該注意？

答案：**不是靠它自己「悟」，是靠你（或 harness）幫它排優先級。**

### 常見優先級策略（由高到低）

| 優先級 | 放什麼 | 為什麼 |
|---|---|---|
| P0 | 當前任務目標 + 硬性規則 | 決定「這次要完成什麼」 |
| P1 | 最新用戶問題 / 最新工具結果 | 最近資訊通常最相關 |
| P2 | 濃縮後的決策與約束 | 「已確認用繁中」「不可洩題」 |
| P3 | RAG 命中的高相關片段 | 有根據的知識 |
| P4 | 對話摘要（不是全文） | 保留脈絡但不佔爆窗口 |
| P5 | 較舊的原始訊息 | 能丟就丟，或只留引用 |

### 實務手法

1. **結構化區塊**  
   用明確標題分隔：`## Goal` / `## Constraints` / `## Retrieved Docs` / `## Recent Turns`

2. **把結論往前放、往後放**  
   開頭放目標；結尾再重述「現在請做 X」（對抗 lost-in-the-middle）

3. **釘選（Pinning）**  
   關鍵規則永遠留在 System / 固定前綴，不讓摘要蓋掉

4. **相關性過濾**  
   20 輪裡只有 3 輪跟「出分數題」有關 → 只留那 3 輪 + 摘要

5. **工具結果去噪**  
   長 log 先擷取錯誤行 / 結論，不要整份 JSON dump 進去

### 教育例子：20 輪輔導後如何構建

```
[System] 你是國中數學蘇格拉底助教；練習模式不給最終答案
[Pinned] 學生：小明；弱點：分數加減；本週目標：正確率>80%
[Summary] 前 15 輪摘要：已練同分母，卡在異分母通分
[RAG] 教材 p.42–44 通分步驟（含例題）
[Recent] 最近 3 輪原文（學生最新錯誤）
[Ask] 針對他剛寫的 1/3+1/4，用提問引導下一步
```

這樣模型才知道：**重點是通分引導，不是重聊開頭寒暄。**

## 3. Context Compact（上下文壓縮）

### 是什麼？
當對話變長、工具輸出變多，把舊內容**濃縮成短摘要 / 狀態卡**，騰出窗口給新資訊。

### 為什麼需要？
| 不壓縮 | 壓縮後 |
|---|---|
| Token 爆、又貴又慢 | 成本可控 |
| 噪音變多 | 訊號更清楚 |
| 更容易 lost-in-the-middle | 關鍵約束被保留 |

### 常見壓縮方法

| 方法 | 做法 | 風險 |
|---|---|---|
| **滑動窗口** | 只留最近 K 輪 | 早先重要約束可能丟 |
| **摘要壓縮** | LLM 把舊輪次寫成摘要 | 摘要可能丟細節或失真 |
| **狀態卡** | 維護 `goal/constraints/progress/open_questions` | 要設計好 schema |
| **分層記憶** | 熱記憶（近）/溫（摘要）/冷（外部存） | 實作較複雜 |
| **引用式壓縮** | 只留「檔名+段落 id」，需要時再展開 | 多一次檢索 |

### Compact 的黃金規則
1. **不可壓縮區**：安全規則、用戶硬性偏好、考試模式開關  
2. **可壓縮區**：寒暄、重複解釋、冗長工具 dump  
3. **壓縮後要可驗證**：摘要裡保留「已做決策」與「未決問題」

### 狀態卡範例（建議背這個結構）

```yaml
goal: 完成異分母加減 10 題練習
constraints:
  - 練習模式，不給最終答案
  - 使用繁體中文
progress:
  - 同分母已通過
  - 異分母通分正確率 40%
open_questions:
  - 學生是否理解最小公倍數
last_error: 1/3+1/4 直接加分子分母
```

## 4. Lost in the Middle（迷失在中間）

### 是什麼？
研究與實務都發現：把重要資訊放在 **超長上下文的中段**，模型表現常變差。  
它對 **開頭** 與 **結尾** 通常更敏感，中間容易「看過等於沒看到」。

### 為什麼面試愛問？
因為很多人以為「窗口 200K 就能塞整本教材」——  
**塞得進 ≠ 用得好。**

### 怎麼緩解？

| 策略 | 做法 |
|---|---|
| 重排位置 | 關鍵約束放開頭；任務指令放結尾再強調一次 |
| 縮短中段 | 中間只放高相關 RAG，不要整章貼上 |
| 多段檢索 | 用 RAG 取 Top-K，而不是整庫塞入 |
| 明示引用 | 「根據【教材-3】第 2 點…」強迫對齊 |
| 拆任務 | 長文先摘要/抽重點，再進答題 loop |
| 評測 | 用「答案是否引用中段關鍵句」做回歸測試 |

### 一句話記住
> **開頭定規則，中間放精煉證據，結尾下指令。**

---

## 5. 20 輪對話的完整處置流程（請背）

```
每輪結束後：
  1) 更新狀態卡（goal / progress / constraints）
  2) 若 token 超閾值 → Context Compact（摘要舊輪次）
  3) 新問題進來 → 重建 context：
        Pinned 規則
      + 狀態卡
      + RAG（若需要外部知識）
      + 最近少量原文
      + 當前問題（放最後）
  4) 送進模型
```

這就是 **Context Engineering**：不是讓模型「自己記得」，而是系統不斷幫它整理書桌。

---

## 6. 面試對答速查

### Q：上下文很長時，模型怎知道重點？
> 靠結構化構建與優先級：釘選規則、狀態卡、相關性過濾；並把關鍵指令放開頭與結尾，避免 lost-in-the-middle。

### Q：Context Compact 會不會弄丟重要資訊？
> 會，所以要分「不可壓縮區」與「可壓縮區」；壓縮後保留決策與未決問題，必要時可回源展開。

### Q：為什麼不直接把 20 輪全文都留著？
> 貴、慢、噪音大，且中段資訊更容易被忽略；保留全文不如保留正確的狀態。

## 小測驗

1. 什麼是 Lost in the Middle？如何緩解？  
2. Context Compact 的「不可壓縮區」通常放什麼？  
3. 用自己的話說明：20 輪後如何重建上下文。

<details>
<summary>參考答案</summary>

1. 長上下文中段資訊易被忽略；把關鍵放兩端、縮短中段、用 RAG Top-K  
2. 安全規則、硬性偏好、模式開關、已確認的關鍵約束  
3. 狀態卡 + 釘選規則 + 精煉 RAG + 最近原文 + 當前問題放最後  

</details>
